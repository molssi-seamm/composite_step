classmethod get_model_chemistry_options(periodic_only=False, mdi_only=False, data_path=None)[source]#

The composite methods SEAMM provides: SEAMM:CMP@<recipe> for the newest version of each recipe found.

The recipes are the shipped set plus those in a recipes/ directory of each data_path entry (a job’s data, the user’s). Composites are molecular and have no MDI engine or gradients yet, so a periodic-only or MDI-only request gets nothing.

Whether the codes for a recipe’s components are installed is not checked here: that needs the other steps’ model chemistries, and asking for them from inside model-chemistry discovery would recurse. The step checks it before it runs anything (composite_step.recipes.check_capabilities()).

composite_step.evaluate module#

Running a recipe: its components as ordinary calculations, then the combination.

Each component is an ordinary single point at the recipe’s geometry, run through its own model chemistry (ORCA:DFT@...) by seamm_exec’s Evaluator: one evaluator per component over all the structures, so the structures of a component run in parallel, as tasks or over MDI as the Evaluator chooses. Each component’s result is the code’s ordinary result with its ordinary calculation record and settings fingerprint, so the fragment store finds and keeps components, never composites, and a component shared by two recipes is computed once.

Energies are combined in kJ/mol, as the Evaluator returns them. Every result of a combine block scales like an energy (homogeneous of degree 1 in the energies, checked when the recipe is read: see composite_step.recipes.DEGREES), so the result is the same in any unit; only the empirical constants, which recipes give in E_h, are converted here. A recipe of one component therefore gives exactly that component’s energy, with no unit conversion of it.

composite_step.recipes module#

Composite-method recipes: the file format, its checks, the combination of the component energies, the capability check and the thermal terms.

A recipe is a declarative YAML file that says exactly how an energy is made from ordinary calculations: the geometry and frequency level, the single-point components at that geometry, and an expression (combine) that combines them. The result is itself a model chemistry, SEAMM:CMP@<recipe>.

This module has no GUI and no SEAMM flowchart dependencies, so it can be used and tested on its own. See NOTES_composite_methods.md (the design) for the reasons.

Units: a recipe’s empirical constants are in hartree (E_h). Every result of combine must scale like an energy (degree 1 in the energies; checked when the recipe is read), so the components may be combined in any one unit, E_h or kJ/mol, with the constants in the same unit. The thermal terms likewise.

class composite_step.substep.Substep(flowchart=None, title='no title', extension=None, logger=<Logger composite_step.substep (WARNING)>, module=None)[source]#

Bases: Node

A base class for substeps in the Composite subflowchart.

The top-level Composite step iterates over the substeps of its subflowchart and calls each substep’s run() method. Each substep is responsible for preparing its own input, invoking Composite, analyzing its output, and storing its results.

This base class provides:

  • is_runable - whether the top-level loop should call run() on this substep. Override to return False for substeps that only contribute input (e.g., an Initialization step) rather than invoking the code.

  • input_only - a flag for “write input but don’t run” mode, useful for debugging and testing.

  • options / global_options - delegated to the parent step so that command-line options reach substeps uniformly.

  • header - a printable header for this section of step.out.

  • version / git_revision - delegated to the plug-in package so that every substep reports the plug-in’s version, not seamm.Node’s.
